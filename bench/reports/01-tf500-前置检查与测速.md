## XTier DeepSeek 加速包源码核查

XTier v0.1.6 的 `xtier/packs/deepseek_v4` 包含 SM120 的 FP8 GEMM 调优与小批量 b12x 内核、FP8 `wo_a`、分页索引器、DSpark 草稿 FP8 词表头，以及 Engram 行存 NVMe 时的预取；另有针对低于 SM90 GPU 的兼容内核。其主运行路径是 CPU/GPU 分层 MoE，项目自带 DeepSeek 启动脚本以单卡 RTX PRO 5000、50 个热专家槽、Engram NVMe 行存为默认配置。当前八卡服务 `XTIER=0`，插件 `load()` 直接返回，上述加速钩子均未启用；服务实际使用 SGLang TP8、Humming、DSpark，模型与 Engram 内存均可容纳，无需为了容量把 Engram 放 NVMe。

项目 README 的单卡对照（XTier 混合推理关加速包 → 开加速包）：decode 每步 50.9→29.9ms（耗时下降 41%），长回复 65.5→151.5tok/s；冷 prefill 64K 为 3318→5561tok/s、500K 为 3627→6658tok/s。其基线不是原版 SGLang，且为单卡混合专家路径；八卡 Humming 的收益目前未知，不可把上述比例应用于本机测值。源码见 [DeepSeek 包](https://github.com/a775828b-dot/xtier/blob/main/xtier/packs/deepseek_v4/__init__.py)、[项目测速表](https://github.com/a775828b-dot/xtier/blob/main/README.md#deepseek-v41-flash-1017)。

### 迁移前静态评估（历史记录）

原 XTier 插件的 `load()` 在 `XTIER=0` 时不安装任何钩子；改成 `XTIER=1` 会连 CPU/GPU 混合 MoE 后端一起安装，不符合八卡 Humming 的目标。下表是迁移前的源码兼容性判断，后续已实施的改动和实测见文末。

| 加速项 | 迁移判断 | 当前八卡适用性 |
| --- | --- | --- |
| SM120 分页索引器 | 可迁；把 `decode_scores` 的 SM120 分支显式接入分页打分与 top-k，避免照搬全局 `get_platform` 临时替换 | 有潜力，特别是长上下文；TP8/64 并发需验证 |
| `wo_a` FP8 权重与小批量 Triton 核 | 可迁；与 MoE 后端独立，但需验证 TP8 张量形状、逐层数值和显存 | 默认只处理 ≤16 行，20/64 并发 verify 通常超出，收益不能照搬单卡 |
| FlashInfer b12x 小批量 FP8 GEMM | 可迁为 `fp8_utils` 的小行数分流 | 当前服务已用 `flashinfer_cutlass`；默认只处理 1–24 行，大批量通常不命中 |
| DSpark 草稿 FP8 词表头 | 可迁，但当前 SGLang 已有 Blackwell 原生 `--speculative-dspark-lm-head-dtype mxfp8`，应先与该实现比较 | 草稿路径可用；增加一份量化词表头的显存，具体收益未测 |
| SM120 候选索引器回退 | 当前 SGLang 已内建 dense-block 回退 | 无需重复迁移 |
| W8A8 调优配置 | 现有 11 份文件仅匹配 RTX PRO 5000 的设备名，且当前服务使用 FlashInfer CUTLASS | 不能直接用于 RTX 6000D；需重新调优才有意义 |
| Engram NVMe 行存/预取 | 独立于 MoE，但本机 1TiB RAM 已容纳 Engram | 当前不需要；不能把单卡的收益算进八卡预期 |
| 低于 SM90 的兼容核、compact verify 修正 | 本机 SM120 且使用 static verify | 无需迁移 |

因此可迁移的优先顺序是分页索引器、`wo_a`、b12x，然后比较原生 DSpark mxfp8。XTier 单卡加速数据中的冷 prefill 大幅提升含混合专家分块、热槽及 CPU 分担等策略，不是独立加速包在八卡全显存路径上的可兑现增益。**推测**：20/64 并发的提升会小于单卡混合推理表格所示比例；具体数值无八卡 A/B 证据，不给预测值。

若实测与计划预估差距较大，以原始结果为准，不把预估写成验收通过。

## xtier_86kd 独立加速包与开发测速

私有仓库 `https://github.com/a775828b-dot/xtier_86kd` 已收纳 XTier 的完整 DeepSeek 加速包、SM120 兼容修复、可选 Engram NVMe 行存源码和测速脚本。服务器源码位于 `/data/src/xtier_86kd`，以 editable 方式装入 `/data/xtier-env`。正式服务保留 `XTIER=0`，使用 `XTIER_86KD=1` 独立启用加速包，不接管 Humming MoE。Engram 仍在主机内存，其余模型权重在八卡显存。服务器的 TP8 层中 40/40 个 `wo_a` 层转换为 FP8；DSpark 草稿词表头 FP8 已启用。B12x 小批量核在 TP8 的 K=288 专家路径会回退到 CUTLASS，避免原内核形状限制；配置 JSON 原为 PRO 5000 调优，不匹配本机 PRO 6000D，不计入性能收益。

静态验证模式初测（短提示、512 输出 token）：20 并发 20/20 成功，`decode_window_tps` 从原服务 1291.78 变为 1268.54 tok/s，差 -1.8%；新服务 `successful_output_tps` 1217.36 tok/s，原服务 977.91 tok/s，但首字与缓存状态不同，不应将端到端差值归因于加速包。单请求短测成功。原始文件 `/data/bench/serving-86kd-static-c1-c20.json`，基线 `/data/bench/serving-final-078-c20-c64.json`。

参照 XTier 的 `agent_bench` 跑了 64K 与 128K 编码代理会话，4 步/会话，8/8 请求成功且均调用工具；静态模式合计 decode 622.5 tok/s，验证步均值 8.69ms；64K、128K 会话分别 650.0、601.4 tok/s。首个 64K 冷请求 TTFT 78.266 秒，128K 冷请求 10.263 秒；两者差异很大，可能含启动后额外开销，不能据此推断长度扩展规律。后续缓存请求 TTFT 中位 1.21 秒。原始文件 `/data/bench/agent-86kd-static.json`。

开发阶段按用户指定固定 32K 输入、1K 输出，测单发及 4、8、16、32 并发。测速分两段：先发独立 32K 冷提示、每路只输出 1 token，`prefill_window_tps_est` 为总输入 token 除以全批首字窗口；再清缓存、预热一份公共 32K 前缀，让所有请求共享该前缀并各输出 1K，`decode_window_tps` 为总输出 token 除以全批输出窗口。共享前缀使 32 路解码的缓存命中保持约 99%；若用 32 条独立前缀，即使清缓存并分批回填，32 路仅有约 20 条被保留，二段请求会重新 prefill，无法作为纯解码对照。每轮记录成功数、缓存命中、每步接受 token 和每请求平均验证步耗时。该步耗时包括调度等待，非单独 GPU 核耗时。
